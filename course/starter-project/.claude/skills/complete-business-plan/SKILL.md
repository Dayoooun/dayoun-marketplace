# 사업계획서 처음부터 끝까지

사용자가 가진 자료와 공식 기준을 먼저 잠근 뒤 필요한 만큼만 진행한다. 특정 기관의
기준을 기본값으로 가정하지 않고, 사용자가 제공한 최신 공식 원문을 최우선으로 삼는다.

## 설치 후 기본 리드 계약

사용자는 스킬 이름, 폴더 구조, 명령어, XML, 디자인 규격을 알 필요가 없다. 자연어로
원하는 결과와 자료를 주면 에이전트가 다음 순서로 작업을 리드한다.

1. 사용자가 요구한 최종 산출물·마감·공식 양식·금지사항을 `고정 조건`으로 선언한다.
2. 제공 파일과 기존 프로젝트를 먼저 읽고 이미 확인된 내용은 다시 묻지 않는다.
3. 신청·제출용과 강사가 참여자 답변·승인을 기록하는 실제 교육은 `REAL`로 정한다. 사용자가 자동·무인 강의시연 또는 회귀검증이라고 명시한 경우만 `DEMO`로 정한다.
4. 목적, 현재 근거, 빠진 결정, 즉시 실행할 작업을 짧은 작업 브리프로 정리한다.
5. 원본 보존, 공식 자료·양식·회사·아이디어 분석처럼 되돌릴 수 있는 일은 질문을 기다리지 않고 진행한다. 외부 조사는 3단계 방향 인터뷰가 확정된 뒤 시작한다.
6. 고객·제품·전략 선택, 문안 승인, 공개범위, 제출처럼 결과를 바꾸는 결정만 권장안과 대안을 함께 제시해 확인받는다.
7. 선택지가 여럿이면 평가기준과 근거에 가장 맞는 안을 먼저 권장한다. 선택지만 나열하고 사용자가 전체 절차를 설계하게 하지 않는다.
8. 각 단계가 끝나면 통과한 근거, 남은 위험, 다음 사용자 결정을 한 화면 안에 보여 준다.

사용자의 명시적 지시는 공통 기본값보다 항상 우선한다. 지시가 충돌하면 어느 요구를
우선하면 무엇이 달라지는지 한 번 설명하고, 사용자의 선택을 고정 조건으로 기록한다.
`알아서`, `전문적으로`, `보기 좋게`라는 요청은 임의 창작 허가가 아니라 근거 안에서
구조·표현·디자인 결정을 주도하라는 뜻으로 해석한다.

첫 요청을 정규화하기 전에 기존 사업계획서 프로젝트 루트가 있는지 확인한다. 새 작업이면
`../setup-business-plan-project/scripts/create_project.py`로 프로젝트를 먼저 만들고, 기존
작업이면 현재 루트를 그대로 사용한다. 그 다음 사용자 원문을 UTF-8
`00. 시작하기/사용자요청.txt`에 저장하고, 이 SKILL.md가 있는 폴더의
`scripts/lead_request.py`로 `00. 시작하기/리드브리프.json`을 만든다.
프로젝트 루트의 scripts로 해석하지 않는다.

Windows:

```powershell
python "<이 SKILL.md가 있는 폴더>\scripts\lead_request.py" --request-file "사용자요청.txt" --output "00. 시작하기\리드브리프.json"
```

macOS/Linux:

```bash
python3 "<이 SKILL.md가 있는 폴더>/scripts/lead_request.py" --request-file "사용자요청.txt" --output "00. 시작하기/리드브리프.json"
```

리드브리프의 `nextAction`과 `autonomousActions`는 바로 실행한다. `materialDecisions`는
해당 조건이 실제로 남아 있을 때만 질문하며, `contentApproval`을 에이전트가 채우지 않는다.
`lead_request.py`와 프로젝트 생성기는 항상 REAL을 기본값으로 쓴다. 자동·무인 강의시연
또는 회귀검증이라고 명시한 경우에만 두 명령 모두에 `--mode DEMO`를 전달한다.
`purpose=교육`, 강사 참여, 참가자 인터뷰·승인이 하나라도 있으면 REAL이 우선한다.
`데모데이 제출용`처럼 사업 내용에 `데모`가 포함된 문장을 보고 DEMO로 추론하지 않는다.

## 먼저 공식 입력을 잠근다

공고문·평가지표·작성지침·사업계획서 양식·FAQ·수정공고가 있으면 먼저 목록을 만들고
서로 다른 버전과 날짜를 확인한다. 공식 자료에 있는 내용을 사용자에게 다시 묻지 않는다.

## 핵심 정보가 비어 있으면 하나만 묻기

공식 입력과 기존 자료를 확인한 뒤에도 사업 아이디어의 **고객·사용 상황·문제**가
비어 있으면 다음 질문 하나만 하고 답을 기다린다.

> 누가, 어떤 상황에서, 어떤 문제를 해결하기 위해 이 사업을 이용하나요? 아직 모르면 모른다고 적어 주세요.

사용자가 이미 말한 내용은 다시 묻지 않는다.

## 조사 전에 방향을 확정한다

공식 입력과 사용자 자료를 분석한 뒤 하네스가 자료의 모호성을 먼저 찾고 사용자에게
역질문한다. 사용자가 질문 목록을 설계하게 하지 않는다. 필수 결정은 고객·사용 상황·문제·
첫 제품 또는 서비스·판매 방식·조사 우선순위·중단 또는 변경 기준이다.

각 결정은 `확인됨 / 모호함 / 모름 / 보류`로 분류한다. 출처가 하나이고 답이 분명한 항목은
다시 묻지 않고 `확인됨`으로 제시한다. 답이 여러 가지로 해석되거나 근거가 충돌하면 다음
순서로 **한 번에 한 질문만** 묻고 답을 기다린다.

1. 현재 자료에서 확인한 사실과 모호한 지점을 한 문장으로 설명한다.
2. 평가기준과 근거에 맞는 2~3개 선택지, 각 선택의 영향, 권장안을 제시한다.
3. 사용자의 답을 한 문장으로 되짚어 해석이 맞는지 확인한다.
4. 확인된 답·근거 파일·결정한 사람·시각을 `04. 조사자료/방향결정.md`와
   `00. 시작하기/사용자협업상태.json`에 즉시 기록한다.
5. 새 답 때문에 다른 항목이 모호해지면 그 항목을 질문 대기열에 넣는다.

모든 필수 결정이 `확인됨`이거나 사용자가 `보류`를 명시하고 그 영향이 BLOCK으로 기록될
때까지 인터뷰를 계속한다. 사용자가 “알아서 정해줘”라고 해도 하네스는 근거에 맞는 권장안을
제시한 뒤 선택을 확인하며 스스로 승인하지 않는다. 방향 확인은 최종 전략 승인이 아니라
조사 범위와 우선순위를 잠그는 게이트다. 완료 전에는 외부 조사 worker를 시작하지 않는다.

## 지원하는 작업

- 새로 작성: 아이디어와 자료에서 사업계획서의 뼈대와 초안을 만든다.
- 기존 문서 보완: 현재 문서에서 빠졌거나 약한 내용을 찾아 고친다.
- 공고·평가기준 맞춤: 사용자가 제공한 최신 공식 공고, 평가표, 양식을 우선 적용한다.
- 자율 사업계획: 공고가 없으면 독자, 의사결정 목적, 필요한 장·절을 먼저 정한다.

지원사업 신청, 투자·IR, 사내 검토, 대출·제안, 교육 실습 등 용도를 구분한다. 특정 기관의 기준을 기본값으로 가정하지 않는다.

## 1단계 공고·평가지표·지침·양식 분석 계약

지원사업·공모 작업은 초안보다 아래 분석을 먼저 끝낸다.

| 확인 항목 | 기록할 내용 |
|---|---|
| 자격 | 신청 자격, 제외 대상, 지역·업력·업종 조건 |
| 지원 | 지원금, 자부담, 지원 비율, 협약 기간 |
| 일정 | 접수 시작·마감 시각, 평가·발표·협약 일정 |
| 제출 | 제출서류, 파일 형식, 제출 채널, 서명·날인 |
| 평가 | 평가 단계, 항목, 공식 배점, 가점·감점 |
| 작성 | 장·절 질문, 페이지·글자 수, 표·첨부 제한 |
| 변경 | 수정공고·FAQ가 원공고를 바꾼 내용 |
| 근거 | 항목별 원문 파일, 페이지·절, 기준일 |
| 연결 | 공고 요구사항 → 초안 장·절 → 근거 위치 |

산출물은 `공고분석표`, `요구사항-양식-평가지표 연결표`, `확인필요목록`이다.
원문에서 확인되지 않은 값은 추정하지 않고 `확인 필요`로 둔다.

## 처음부터 발표까지 10단계

1. **공고문·평가지표·작성지침·사업계획서 양식 분석**: 위 분석 계약에 따라 공식 요구와 양식 위치를 연결한다.
2. **회사·사업 현황·아이디어 분석**: `setup-business-plan-project`로 원본을 보존하고 사실·미확인 정보·가정·계획을 나눈다.
3. **방향 인터뷰·부족한 근거·확인 질문 도출**: 고객·문제·첫 제품 또는 서비스·판매 방식·조사 우선순위를 사용자와 확인하고, 평가항목별 현재 답변·근거 공백·독립 조사 질문을 만든다.
4. **시장·고객·경쟁·가격·규제 독립 조사**: 방향 확인 뒤 `research-business-evidence`로 서로 겹치지 않는 조사 lane을 실행한다. FULL과 교육 실습은 의미 있는 질문 3개 이상을 만들고 worker 3개 이상을 각각 독립 실행한 뒤 출처·날짜·단위·한계·실패 범위를 기록해 종합한다.
5. **사업전략·실행계획·수익구조 설계**: 문제·고객·해결책·차별점·시장·수익·실행·팀·재무·위험을 연결한다.
6. **평가지표와 양식에 맞춰 텍스트 초안 작성**: `draft-business-plan`으로 HWPX가 아닌 검토 가능한 텍스트 초안을 먼저 만든다. 시각자료가 판단에 도움이 되면 종류·핵심 메시지·근거·표 셀·앞 문단·뒤 문단·짧은 캡션을 함께 설계한다.
7. **검토·수정·사용자 승인**: `review-business-plan`으로 BLOCK을 처리하고 최종 표현과 공개 범위를 승인받는다.
8. **선택한 경우 승인 내용을 HWPX 양식에 반영**: HWPX를 요청했을 때만 수정 가능한 복사본에 `fill-hwpx-template`을 사용한다. 사용자가 한글에서 수정한 HWPX를 다시 올리면 그 최신 파일을 digest-bound `user-edited-canonical`로 승격하고 과거 원본에서 재생성하지 않는다. 시각자료는 답변 셀 마지막이 아니라 명세한 설명 문단 직후에 배치한다.
9. **선택한 HWPX 구조·화면검사**: HWPX를 요청했을 때만 ZIP/XML·원본 고정 구조·스타일 ID 배열 순서·사용자 시각자료 profile·deletion receipt·미치환·Preview 동기화를 검사하고, 실제 렌더러로 PDF와 페이지별 PNG를 만든 뒤 전체 페이지·100%·확대 화면에서 표·줄바꿈·페이지 넘김·잘림·겹침을 검사한다.
10. **선택한 PPT·대본·예상 Q&A 제작**: PPT를 요청했을 때 `ppt-editorial`이 승인 canonical을 발표용 메시지로 재구성한다. HWPX 입력이나 검증 기록은 요구하지 않는다.

### 10단계 순차 실행 강제

작업을 시작하기 전에 `../setup-business-plan-project/scripts/create_project.py`로
`00. 시작하기`부터 `99. 원본백업`까지 강제 구조를 만든다. 입력 참고 폴더에는
파일이나 폴더를 새로 만들지 않는다.

각 단계는 `../setup-business-plan-project/scripts/advance_stage.py`의 `start`로 시작하고,
해당 번호 폴더에 산출물을 저장한 뒤 실제 파일 경로를 evidence로 `complete`한다.
1~7단계는 PASS 없이 건너뛸 수 없다. 8~10단계는 선택하지 않았을 때만
NOT_REQUESTED로 기록한다. BLOCK인 단계가 있으면 다음 단계의 작성·HWPX·PPT를
시작하지 않는다.

`DEMO`는 자동·무인 회귀검증과 자동 강의 fixture에만 쓴다. 강사가 참여자와 역질문·답변·
승인을 기록하는 교육은 `REAL`에서 사용자 답을 `00. 시작하기/사용자협업상태.json`에
기록하면서 함께 범위를 좁힌다.
특히 3단계 방향·질문 확인, 5단계 전략 선택, 7단계 문안 승인, 8단계 HWPX 선택,
10단계 발표자료 선택을 에이전트가 대신 결정하지 않는다. 방향 확인 전에는 공식 자료·양식·
회사·아이디어와 기존 근거만 분석할 수 있으며 외부 조사 worker를 시작하면 안 된다. 방향
확인 뒤 서로 독립적인 조사와 문서 분석은 병렬로 진행하되 사용자 선택이 필요한 값을
확정하지 않는다.
DEMO/PARTIAL은 사용자 승인을 대신하지 않으므로 7단계를 BLOCK으로 닫고 8~10단계를
시작하지 않는다. 단계별 evidence는 해당 단계 산출 폴더의 새 파일이어야 한다.

실제 강사가 참여자와 인터뷰하고 승인을 기록하는 교육 실습은 `REAL` 모드에서
`purpose=교육`으로 실행한다. 자동·무인 회귀검증만 `DEMO`를 사용한다.

### 시각자료 기본값

시각자료를 선택하면 `../fill-hwpx-template/references/visual-design-system.md`를 따른다.
답변 셀 마지막 일괄 배치는 금지하고 `앞 문단 / 뒤 문단`으로 의미상 위치를 고정한다.
별도 디자인 요구가 없을 때만 Pretendard와 밝고 절제된 정보 디자인을 기본으로 사용한다.
공식 양식, 사용자 요구, 브랜드 기준이 이 기본값보다 우선하며 원본 쪽 여백은 바꾸지 않는다.

사용자가 HWPX 디자인을 요청하거나 `알아서 보기 좋게`라고 하면 `fill-hwpx-template`이
원본 양식의 쪽·표·문단 구조와 질문별 정보밀도를 먼저 분석한다. 평가자의 판단을
단축하는 문제 구조, 사업모델, 비교표, 실행 로드맵, 예산, KPI만 시각화하고 장식 이미지는
넣지 않는다. 에이전트가 시각자료 종류·레이아웃·배치·타이포·여백을 권장안으로 정하고,
사용자가 지정한 브랜드·색상·스타일이 있으면 그것을 고정 조건으로 적용한다. 승인 문안
반영 뒤 구조검사뿐 아니라 PDF/PNG 렌더를 확대 검수하고 잘림·겹침·페이지 밀도를 고친다.
`알아서·전문적으로·보기 좋게`라는 명시적 디자인 위임은 디자인 권장안의 적용 승인으로
기록한다. 같은 디자인을 다시 허락받지 않는다. 문안·공개범위·제출 승인까지 위임된 것은
아니며, 공식 양식이 여러 개이거나 지시가 충돌하는 경우만 권장안과 대안을 확인받는다.

### 단계 게이트

- 1단계 공식 기준과 2단계 사업정보를 확인하기 전에는 방향 인터뷰와 시장조사 범위를 확정하지 않는다.
- 3단계 방향 확인이 `방향결정.md`와 `사용자협업상태.json`에 기록되기 전에는 외부 조사 worker를 시작하지 않는다.
- FULL과 교육 실습의 4단계는 의미가 겹치지 않는 조사 lane 3개 이상과 worker별 결과·실패 기록·종합본이 없으면 PASS가 아니다. 의미 있는 질문이 3개보다 적으면 억지로 늘리지 말고 사유를 기록해 BLOCK한다.
- 4단계 근거가 핵심 가정을 부정하면 2·3·5단계로 돌아가 계획을 고친다.
- 5단계 전략 연결이 끝나기 전에는 실제 사업계획서 초안을 쓰지 않는다.
- 6단계 초안의 제목을 제외한 모든 주장 문단은 `[E001 | 기관명, {발표연도}]`·`[U001 | 사용자 제공자료, {기록연도}]`·`[H001 | 검증가설]`·`[P001 | 실행계획]`으로 `근거목록.csv`에 연결한다. HWPX 답변은 개조식과 실제 내어쓰기로 통일하고, 최종 본문에는 `(기관명, 연도)` 형식만 보인다. 7단계 출처 추적률이 100%가 아니면 승인·HWPX·PPT를 BLOCK한다.
- 7단계 승인 전에는 선택한 HWPX·PPT를 생성하지 않는다.
- HWPX를 선택했다면 구조검사 PASS, 실제 렌더러가 만든 PDF·페이지별 PNG, 전체 페이지·100%·확대 육안검수 기록 PASS가 모두 있기 전에는 완료라고 말하지 않는다. 렌더러나 렌더 산출물이 없으면 BLOCK이다.
- PPT를 선택했다면 mode 자동검사·fact/structure/contract 검증자 전원 PASS·PPTX/PDF 외부 화면검사가 모두 PASS하기 전에는 PPT 완료라고 말하지 않는다.
- 플러그인에서는 `validators/`, course starter에서는 `.dayoun/validators/`의 fact·structure·contract 스크립트를 각각 실행하고 `aggregate_validators.py`로 합친다. 한 검증자의 PASS나 사람의 판단이 다른 BLOCK을 덮지 않는다.

## 정보 구분

- **내가 알고 있는 정보**: 사용자가 제공한 회사, 팀, 제품, 고객, 실적 정보다. 출처나 확인 상태를 함께 적는다.
- **확인이 필요한 내용**: 시장 규모, 고객 반응, 경쟁 비교처럼 조사나 고객 기록으로 확인해야 할 내용이다.
- **앞으로 할 계획**: 아직 일어나지 않은 일정, 매출, 채용, 개발 계획이다. 현재 실적처럼 쓰지 않는다.

내부 파일에서는 추적을 위해 번호를 붙일 수 있지만, 초보자 안내에는 번호보다 위의 쉬운 이름을 사용한다.

## 완료 기준

작업 시작 시 아래 중 범위를 선언하고, 범위 밖은 완료로 표시하지 않는다.

- QUICK: 가장 중요한 보완점 1개와 근거 1개, 수정안 1개, 다음 행동 1개
- SECTION: 사용자가 선택한 장·절 전체
- FULL: 목적에 필요한 전체 문서와 필수 요구사항

항상 다음을 지킨다.

- 사용자가 주지 않은 실적, 수치, 고객 반응, 계약, 인증을 만들지 않는다.
- 공식 배점이나 요구사항이 없으면 임의 기준을 공식 기준처럼 말하지 않는다.
- 출처의 발표일, 기준연도, 단위, 적용 범위를 함께 기록한다.
- 원본은 보존하고 초안과 최종본을 구분한다.
- 개인정보와 비공개 자료는 제거하거나 가린다.
- 선택하지 않은 HWPX·PPT는 `NOT_REQUESTED`로 기록하고 PASS로 세지 않는다.
- 선택한 HWPX는 원본 고정 구조·패키지 구조검사와 실제 PDF·페이지별 PNG 전체·100%·확대 검수 기록을, 선택한 PPT는 승인 tuple 대조·mode 자동검사·세 검증자·외부 화면검사를 모두 통과해야 한다.

세부 단계와 산출물은 `references/workflow.md`를 읽는다.
